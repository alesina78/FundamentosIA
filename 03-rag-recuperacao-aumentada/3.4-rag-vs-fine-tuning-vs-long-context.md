# 3.4 — RAG vs. Fine-Tuning vs. Long Context

> Três abordagens diferentes para dar a um LLM acesso a conhecimento que ele não tem por
> padrão — cada uma com trade-offs distintos de custo, latência e manutenção.

## As três abordagens

| | RAG | Fine-tuning | Long context |
|---|---|---|---|
| **O que faz** | Busca informação relevante e injeta no prompt | Re-treina o modelo com exemplos do seu domínio | Coloca todo o conteúdo relevante direto no prompt |
| **Dado muda com frequência?** | ✅ Ótimo — atualiza a base sem re-treinar | ❌ Ruim — precisa re-treinar a cada mudança | ✅ Ok, mas reenviar tudo a cada chamada tem custo |
| **Custo por chamada** | Baixo/médio (busca + prompt menor) | Baixo (prompt normal, sem overhead) | Alto (muitos tokens de input a cada chamada) |
| **Custo de setup** | Médio (pipeline de indexação) | Alto (dataset de treino, tempo de treino) | Baixo (nenhum setup adicional) |
| **Muda o "comportamento" do modelo?** | Não — só adiciona contexto factual | Sim — pode mudar tom, estilo, formato de resposta | Não — só adiciona contexto factual |
| **Latência** | Adiciona a etapa de busca | Nenhuma latência extra | Processar mais tokens de input aumenta latência |

## Quando usar cada uma

**RAG** — o caso mais comum. Use quando:
- Você tem uma base de conhecimento que muda com frequência (documentação, catálogo, políticas).
- Você precisa citar a fonte da informação.
- Você quer controlar exatamente qual informação está disponível para cada pergunta.

**Fine-tuning** — use quando:
- Você quer mudar o **comportamento** do modelo (tom, formato específico, jargão do domínio), não só adicionar fatos.
- Você tem um volume grande e estável de exemplos de alta qualidade.
- Latência e custo por chamada são mais críticos que o custo de setup.

**Long context** — use quando:
- A base de conhecimento é pequena o suficiente para caber inteira no context window.
- Você não quer construir um pipeline de retrieval (menos peças móveis).
- A informação não muda entre chamadas na mesma sessão — nesse caso, **prompt caching**
  (aula 1.2) reduz bastante o custo de reenviar o mesmo contexto grande repetidamente.

## Elas não são mutuamente exclusivas

Na prática, é comum combinar: um sistema pode usar **RAG** para buscar os documentos mais
relevantes, colocar esses poucos documentos no **contexto** da chamada (não o contexto
inteiro possível — só o que a busca trouxe), e o modelo já ter sido **fine-tuned** para
responder num formato específico da empresa. As três técnicas resolvem problemas
diferentes e podem coexistir no mesmo sistema.

## Árvore de decisão simplificada

```
A base de conhecimento muda com frequência?
├── Sim → RAG
└── Não
    ├── Cabe inteira no context window? → Long context (+ prompt caching)
    └── Não cabe → RAG

Preciso mudar o COMPORTAMENTO do modelo (não só os fatos)?
└── Sim → considere fine-tuning (frequentemente combinado com RAG para os fatos)
```

## Pontos-Chave

✅ RAG resolve dados que mudam com frequência, sem re-treinar o modelo.
✅ Fine-tuning muda comportamento (tom, formato), não é a ferramenta certa só para adicionar fatos.
✅ Long context é simples de implementar, mas caro se você reenviar o mesmo contexto grande em toda chamada — combine com prompt caching.
✅ As três técnicas podem ser combinadas no mesmo sistema.
