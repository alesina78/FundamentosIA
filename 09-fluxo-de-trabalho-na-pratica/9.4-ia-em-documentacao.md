# 9.4 — IA em Documentação

> Documentação escrita a partir do **código real** (a fonte da verdade) tende a ficar mais
> precisa e atualizada do que documentação escrita separadamente e mantida manualmente em
> sincronia — um problema clássico que boa parte dos times conhece bem.

## O problema da documentação desatualizada

Documentação que vive separada do código tende a "descolar" da realidade com o tempo: o
código muda, ninguém lembra de atualizar o README, e a documentação passa a descrever um
comportamento que não existe mais. Gerar documentação **a partir** do código-fonte reduz
esse risco — cada vez que o código muda, você pode regenerar a documentação correspondente.

## Exemplo em Python — de código para docstring e README

Código completo: [`exemplos-python/9.4_gerar_documentacao_a_partir_do_codigo.py`](exemplos-python/9.4_gerar_documentacao_a_partir_do_codigo.py)

```python
def gerar_docstring(codigo: str) -> str:
    prompt = f"""\
Adicione uma docstring no formato Google Style à função abaixo, documentando
parâmetros, retorno e exceções levantadas. Não mude a lógica do código, apenas
adicione a docstring.

```python
{codigo}
```
"""
    ...

def gerar_trecho_readme(codigo_com_docs: str) -> str:
    prompt = f"""\
Com base na função documentada abaixo, escreva um trecho de README em Markdown
explicando o que ela faz, com um exemplo de uso.
"""
    ...
```

Note a instrução **"não mude a lógica do código, apenas adicione a docstring"** — isso
restringe o escopo da tarefa (mesmo princípio da aula 9.2) e evita que o modelo aproveite
para "melhorar" código que não foi pedido para mudar.

## O que revisar em documentação gerada por IA

| Risco | O que checar |
|---|---|
| Docstring descreve comportamento que não bate com o código | Comparar cada afirmação da doc contra o código real |
| Exemplos de uso que não funcionam de verdade | Rodar o exemplo, não só ler |
| Tom/nível de detalhe inconsistente com o resto da documentação do projeto | Ajustar manualmente ou fornecer exemplos do estilo esperado no prompt |
| Documentação genérica demais, sem capturar nuances do domínio | Complementar manualmente com contexto que só um humano do time tem |

## Quando manter documentação gerada automaticamente

Documentação gerada é um bom ponto de partida, especialmente para código sem documentação
nenhuma — mas documentação de alto nível (arquitetura, decisões de design, "por que"
alguma coisa foi feita de um jeito específico) geralmente precisa de contexto que só existe
na cabeça do time, e vale a pena escrever manualmente. Um bom padrão: use IA para
documentação de **referência** (o que uma função faz, parâmetros, exemplos), e escreva
manualmente a documentação de **contexto** (por que essa decisão de arquitetura foi
tomada).

## Fechando o módulo: o fluxo completo

Ao longo do módulo 9, vimos o ciclo completo de como IA se encaixa no desenvolvimento de
software:

```
9.1 Design/planejamento → 9.2 Escrita de código → 9.3 Testes/revisão → 9.4 Documentação
```

Em cada etapa, o padrão se repete: **IA acelera a parte mecânica/repetitiva, humano revisa
e decide**. Isso não é um detalhe incidental — é o princípio central deste curso inteiro,
desde os fundamentos de LLMs (módulo 1) até aqui: usar IA de forma eficaz não significa
delegar julgamento, significa saber exatamente onde ela ajuda e onde a responsabilidade
continua sendo sua.

## Pontos-Chave

✅ Documentação gerada a partir do código real tende a ficar mais precisa que documentação mantida separadamente.
✅ Restringir o escopo do pedido ("só documente, não mude a lógica") evita mudanças não solicitadas.
✅ Sempre valide exemplos de uso gerados — rode-os, não confie apenas na leitura.
✅ Use IA para documentação de referência; documentação de contexto/decisão geralmente precisa de um humano.
