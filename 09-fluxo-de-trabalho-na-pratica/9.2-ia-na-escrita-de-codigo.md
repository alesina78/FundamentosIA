# 9.2 — IA na Escrita de Código

> A produtividade real de usar IA para escrever código vem de mudanças **pequenas,
> revisáveis e justificadas** — não de pedir para gerar um sistema inteiro de uma vez e
> confiar sem revisar.

## Mudanças incrementais em vez de "gere tudo de uma vez"

Pedir para uma IA gerar um sistema inteiro em um único prompt parece rápido, mas produz
código difícil de revisar — você não consegue avaliar cada decisão isoladamente. O padrão
mais sustentável é: pedir mudanças pequenas e específicas, revisar cada uma, e só então
seguir para a próxima.

```
❌ "Crie um sistema completo de checkout com carrinho, cupom, frete e pagamento."
✅ "Adicione a função de calcular frete grátis para pedidos abaixo de 1kg e 10km."
   (revisar) → próxima mudança pequena → (revisar) → ...
```

Isso é a mesma lógica do módulo 7 (SDD) aplicada em escala menor: cada mudança pequena é,
na prática, uma mini-spec.

## Exemplo em Python — pedir mudança com justificativa e suposições explícitas

Código completo: [`exemplos-python/9.2_gerar_codigo_com_justificativa.py`](exemplos-python/9.2_gerar_codigo_com_justificativa.py)

```python
prompt = f"""\
Código atual:
```python
{codigo}
```

Pedido de mudança: {pedido}

Instruções:
1. Faça APENAS a mudança pedida — não refatore ou "melhore" outras partes do código.
2. Depois do código, explique em 1-2 frases o que mudou e por quê.
3. Se o pedido for ambíguo em algum ponto, diga qual suposição você fez.
"""
```

Três instruções fazem trabalho pesado aqui: **restringir o escopo** (só a mudança pedida,
sem "melhorias" não solicitadas que dificultam a revisão), **pedir justificativa** (você
revisa a explicação, não só o código) e **expor suposições** (ambiguidades do pedido viram
decisões implícitas do modelo — melhor que fiquem explícitas para você validar).

## Revisão de código gerado por IA não é opcional

Assim como qualquer código escrito por um humano júnior passa por code review antes de ir
para produção, código gerado por IA merece o mesmo tratamento — talvez mais, já que o
modelo não tem o contexto completo do seu sistema, dos débitos técnicos conhecidos, ou de
decisões arquiteturais implícitas que nunca foram documentadas. Isso conecta com o módulo
8.4 (revisão humana): código é uma forma de "decisão" que também merece essa camada.

## Boas práticas na prática do dia a dia

| Prática | Por quê |
|---|---|
| Peça mudanças pequenas, revise cada uma | Facilita identificar onde algo saiu errado |
| Restrinja o escopo explicitamente ("só isso, não refatore o resto") | Evita mudanças não solicitadas difíceis de revisar |
| Peça para o modelo expor suposições/ambiguidades | Transforma decisões implícitas em decisões visíveis |
| Nunca aplique código sem ler | Mesmo em harnesses com boa autonomia (módulo 6), revisão continua sendo sua |
| Use um harness com boas permissions (módulo 6.3) | Reduz o risco de uma mudança grande demais ser aplicada sem revisão |

## Pontos-Chave

✅ Mudanças pequenas e revisáveis produzem código mais confiável do que pedir tudo de uma vez.
✅ Restringir o escopo do pedido evita "melhorias" não solicitadas que dificultam a revisão.
✅ Pedir justificativa e suposições explícitas transforma decisões implícitas do modelo em algo revisável.
✅ Revisão humana de código gerado por IA não é opcional — é parte do processo, não um passo extra.
