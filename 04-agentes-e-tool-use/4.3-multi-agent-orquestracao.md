# 4.3 — Multi-Agent e Orquestração

> **Sistema multi-agente**: em vez de um único LLM tentando resolver toda a tarefa, o
> problema é dividido entre vários "agentes" especializados (cada um uma chamada de API
> com um papel e contexto específicos), coordenados por um orquestrador.

## Por que dividir em vários agentes

Um único agente com um prompt genérico "faça tudo" tende a ser mediano em cada parte da
tarefa. Dividir em agentes especializados — cada um com um system prompt focado em uma
subtarefa — costuma produzir melhor resultado por parte, ao custo de mais chamadas
(latência e dinheiro).

| Um agente genérico | Múltiplos agentes especializados |
|---|---|
| Um prompt tenta cobrir tudo | Cada agente tem um papel e contexto focado |
| Mais simples de implementar | Mais chamadas de API = mais custo e latência |
| Pode "misturar" responsabilidades numa resposta só | Cada etapa pode ser avaliada e ajustada isoladamente |
| Bom para tarefas simples | Vale a pena para tarefas com etapas bem distintas (pesquisar → escrever → revisar) |

## Padrão orquestrador-trabalhador (orchestrator-worker)

Um agente "coordenador" decide a sequência de sub-tarefas e delega para agentes
especializados, agregando os resultados. A orquestração pode ser:

- **Fixa**: seu código Python decide a sequência (ex: sempre pesquisar → depois escrever).
- **Dinâmica**: o próprio LLM coordenador decide quem chamar, usando tool use (aula 4.1),
  onde cada "ferramenta" é, na verdade, uma chamada a outro agente especializado.

## Exemplo em Python — orquestração sequencial fixa

Código completo: [`exemplos-python/4.3_multi_agent_orquestracao.py`](exemplos-python/4.3_multi_agent_orquestracao.py)

```python
def orquestrador(topico: str) -> str:
    pontos_chave = agente_pesquisador(topico)   # 1º agente: levanta os fatos
    texto_final = agente_redator(topico, pontos_chave)  # 2º agente: escreve o texto final
    return texto_final
```

Cada agente é só uma chamada `client.messages.create` com um `system` prompt diferente,
focado numa única responsabilidade. O "orquestrador" aqui é simplesmente a função Python
que decide a ordem e repassa o resultado de um agente para o próximo.

## Trade-offs a considerar

| Fator | Impacto de usar multi-agente |
|---|---|
| **Custo** | Cada agente é uma chamada de API separada — custo soma |
| **Latência** | Chamadas sequenciais somam tempo (a menos que sejam paralelizáveis) |
| **Qualidade** | Agentes focados tendem a fazer melhor sua parte específica |
| **Complexidade** | Mais peças móveis para depurar quando algo dá errado |
| **Paralelismo** | Sub-tarefas independentes podem rodar em paralelo, reduzindo latência total |

## Quando NÃO vale a pena

Para tarefas simples e diretas, dividir em múltiplos agentes só adiciona custo e latência
sem ganho de qualidade perceptível. Multi-agente compensa quando a tarefa tem etapas
genuinamente distintas (ex: pesquisar fatos vs. escrever com boa prosa) que se beneficiam
de um "papel" e contexto dedicados.

## Pontos-Chave

✅ Multi-agente divide uma tarefa complexa entre chamadas especializadas, coordenadas por um orquestrador.
✅ A orquestração pode ser fixa (seu código decide) ou dinâmica (o LLM decide via tool use).
✅ Mais agentes = mais custo e latência — só compensa quando a tarefa tem etapas genuinamente distintas.
✅ Sub-tarefas independentes podem ser paralelizadas para reduzir a latência total.
