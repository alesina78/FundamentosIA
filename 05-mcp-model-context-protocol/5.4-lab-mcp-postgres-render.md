# 5.4 — Lab: um servidor MCP sobre um Postgres real

> Até aqui o servidor MCP devolvia dados de um dicionário em memória. Neste laboratório
> o dado sai de um **banco Postgres hospedado no Render**, inspecionado pelo **DBeaver**
> e exposto ao modelo por um **servidor MCP** — o caminho completo, ponta a ponta.

## O que você vai montar

```
Claude Code / Claude Desktop   →   servidor MCP (Python)   →   Postgres (Render)
        (host + client)              (5.4_servidor_...py)        (nuvem, TLS)
                                                ↑
                                          DBeaver (você, inspecionando o mesmo banco)
```

O DBeaver não faz parte do fluxo do agente: ele é a sua janela humana para o mesmo banco.
Serve para criar o schema, conferir os dados e — mais importante — **validar se a resposta
que o modelo deu bate com a realidade**. Todo lab de integração precisa de um oráculo
independente; aqui ele é o DBeaver.

## Etapa 1 — Provisionar o Postgres no Render

1. Em [dashboard.render.com](https://dashboard.render.com), **New → Postgres**.
2. Preencha *Name*, *Database* e *User*. Escolha a **região mais próxima** — cada ida e
   volta de query atravessa a internet, e latência aparece nas ferramentas MCP.
3. Escolha o plano **Free** (suficiente para o lab; o Render expira bancos gratuitos após
   ~30 dias, então trate como descartável).
4. Criado o banco, abra a aba **Connections**. Você verá:
   - **Internal Database URL** — só funciona entre serviços dentro do Render.
   - **External Database URL** — é esta que você usa da sua máquina.
   - Host, porta (5432), database, usuário e senha separados.

O Render exige TLS em conexões externas. Isso não é detalhe de configuração: é a razão de
o `sslmode=require` aparecer tanto no DBeaver quanto no código Python.

> ⚠️ A External Database URL contém a senha em texto plano. Ela vai para o `.env`, nunca
> para o repositório. Confirme que `.env` está no `.gitignore` antes de colar qualquer coisa.

## Etapa 2 — Conectar o DBeaver e criar o schema

1. **Database → New Database Connection → PostgreSQL**.
2. Preencha com os campos separados da aba *Connections* do Render (host, porta 5432,
   database, usuário, senha). Marque *Save password*.
3. Aba **SSL** → marque **Use SSL** e defina *SSL mode* como `require`. Sem isso a conexão
   é recusada com um erro genérico de rede, que costuma ser diagnosticado errado.
4. **Test Connection** → o DBeaver oferece baixar o driver JDBC na primeira vez. Aceite.
5. Abra um editor SQL (`Ctrl+]`) e execute o script
   [`exemplos-python/5.4_seed.sql`](exemplos-python/5.4_seed.sql), que cria `cursos`,
   `alunos` e `matriculas` e insere dados de exemplo.

Confira no navegador de banco à esquerda que as três tabelas apareceram em
`Schemas → public → Tables`. Esse é o estado de referência do lab.

## Etapa 3 — O servidor MCP

Código completo: [`exemplos-python/5.4_servidor_mcp_postgres.py`](exemplos-python/5.4_servidor_mcp_postgres.py)

```bash
pip install "mcp[cli]" "psycopg[binary]" python-dotenv
```

Três decisões de projeto merecem atenção, porque são o que separa este servidor do
brinquedo da aula 5.2:

**1. Uma conexão por chamada, não uma global.** Cada ferramenta abre e fecha a conexão.
Um servidor MCP stdio pode ficar horas ocioso enquanto você conversa com o modelo, e o
Postgres derruba conexões paradas — uma conexão global morre silenciosamente e a primeira
chamada depois da pausa falha. Em produção você trocaria isso por um *pool* com
revalidação, não por uma global.

**2. Ferramentas específicas convivem com uma ferramenta genérica.** `listar_cursos` e
`matriculas_do_curso` encapsulam as perguntas que você já sabe que serão feitas: o modelo
não precisa inventar SQL nem conhecer o schema para respondê-las, e o resultado é
previsível. `consulta_sql` cobre o resto — o custo é que o modelo passa a escrever SQL, o
que erra mais e é mais difícil de auditar. A regra prática: **toda pergunta recorrente
vira uma ferramenta nomeada**; a genérica é a válvula de escape.

**3. Somente-leitura, em duas camadas.** A checagem textual (exige `SELECT`, rejeita
palavras de escrita e `;` extra) barra o caso óbvio, mas filtro por regex sobre SQL é
frágil por natureza. Por isso a transação também é marcada `READ ONLY` — o próprio
Postgres recusa a escrita se o filtro falhar. E o `LIMIT 100` externo evita que um
`SELECT *` numa tabela grande estoure a janela de contexto do modelo.

O ideal, num banco de verdade, é ir além: **criar um usuário Postgres com permissão apenas
de `SELECT`** e usar as credenciais dele na `DATABASE_URL`. Aí a garantia deixa de estar
no seu código e passa a estar no banco.

**Resource com o schema.** `banco://schema` lê o `information_schema` e devolve tabelas e
colunas. É o que dá ao modelo a chance de escrever SQL correto sem adivinhar nomes — e
ilustra bem a distinção da aula 5.2: schema é dado de leitura anexável ao contexto, não
uma ação.

## Etapa 4 — Testar antes de conectar

```bash
mcp dev exemplos-python/5.4_servidor_mcp_postgres.py
```

Isso abre o **MCP Inspector** numa página web local (normalmente `http://localhost:6274`).
Ele não é o seu servidor "em modo web": é um client MCP de mentira, que conversa com o seu
servidor por stdio e te deixa chamar tudo na mão.

> ⚠️ **Pré-requisito escondido: Node.js.** O `mcp dev` chama `npx @modelcontextprotocol/inspector`
> por baixo — o Inspector é um pacote Node, não Python. Sem Node/npm instalado o comando
> falha com "npx não encontrado". Note que isso vale **só para o Inspector**: o servidor em
> si é Python puro, e conectá-lo ao Claude Code ou Claude Desktop (etapa 5) não precisa de
> Node. A primeira execução demora mais porque o `npx` baixa o Inspector sob demanda, e
> versões recentes exigem um token — copie do terminal a URL completa, com
> `?MCP_PROXY_AUTH_TOKEN=...`, e não apenas o `localhost:6274`.

Na interface: **Connect** → aba **Tools** → **List Tools**. Devem aparecer as três
ferramentas, cada uma já com o schema derivado da assinatura da função Python.

No inspetor, chame `listar_cursos` sem argumento, depois com `area="IA"`, e leia o resource
`banco://schema`. **Compare cada resultado com o que o DBeaver mostra.** Só depois que as
três respostas baterem faz sentido conectar a um client — depurar erro de conexão através
de uma conversa com o modelo é muito mais lento do que através do inspetor.

## Etapa 5 — Conectar ao client

No Claude Code, a partir da raiz do projeto:

```bash
claude mcp add cursos -- python /caminho/absoluto/5.4_servidor_mcp_postgres.py
```

Caminho **absoluto**: o client sobe o servidor como subprocesso, e o diretório de trabalho
dele não é necessariamente o seu. Pelo mesmo motivo, o `load_dotenv()` pode não achar o
`.env` — se isso acontecer, passe a variável explicitamente com `--env DATABASE_URL=...`
ou aponte o `.env` por caminho absoluto.

Verifique com `/mcp` que o servidor aparece como conectado e pergunte algo como
*"quais cursos de IA estão ativos e quantos alunos cada um tem?"*. O modelo deve encadear
`listar_cursos` e `matriculas_do_curso` — ou escrever um `JOIN` via `consulta_sql`.

Para o Claude Desktop, o equivalente é um bloco em `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "cursos": {
      "command": "python",
      "args": ["C:\\caminho\\absoluto\\5.4_servidor_mcp_postgres.py"],
      "env": { "DATABASE_URL": "postgresql://..." }
    }
  }
}
```

## Quando algo não funciona

| Sintoma | Causa provável |
|---|---|
| `connection refused` / timeout | Usou a *Internal* Database URL em vez da *External* |
| `SSL connection is required` | Faltou `sslmode=require` (no DBeaver, aba SSL) |
| Servidor some do `/mcp` logo após conectar | Exceção na importação — `DATABASE_URL` ausente derruba o processo no `os.environ[...]` |
| Ferramentas aparecem mas toda chamada falha | O `.env` não foi encontrado a partir do diretório de trabalho do client |
| Banco sumiu depois de semanas | Plano free do Render expira; recrie e rode o seed de novo |
| `mcp dev` falha com "npx não encontrado" | Node.js não instalado — é dependência do Inspector, não do servidor |
| Inspector abre mas recusa a conexão | Faltou o `MCP_PROXY_AUTH_TOKEN` na URL; copie a linha inteira do terminal |

## Exercício

Adicione uma ferramenta `matricular_aluno(aluno_id, curso_id)` que **escreve** no banco.
Antes de escrever o código, responda: como o client sinaliza ao usuário que essa ferramenta
tem efeito colateral, e o que muda na sua postura sobre credenciais somente-leitura? Essa
tensão entre utilidade e risco é exatamente o assunto do módulo 8.

## Pontos-Chave

✅ Render entrega Postgres gerenciado com URL externa TLS — `sslmode=require` é obrigatório no DBeaver e no código.
✅ O DBeaver é o oráculo independente do lab: valide as respostas do modelo contra ele.
✅ Abra a conexão por chamada; conexão global em servidor stdio ocioso morre em silêncio.
✅ Perguntas recorrentes viram ferramentas nomeadas; a ferramenta SQL genérica é válvula de escape.
✅ Somente-leitura em camadas: filtro no código, `READ ONLY` na transação e, no ideal, usuário Postgres sem permissão de escrita.
✅ Teste com `mcp dev` antes de conectar ao client — depurar via inspetor é muito mais rápido.
✅ O Inspector é um pacote Node rodado via `npx`: exige Node.js instalado, embora o servidor MCP em si seja Python puro.
