# 2.4 — Avaliando Saídas: do "parece bom" ao eval

> **Eval**: um conjunto fixo de casos de teste mais um critério objetivo de acerto, rodado
> a cada vez que você muda o prompt, o modelo ou os parâmetros — para saber se a mudança
> melhorou ou piorou o resultado, em vez de achar que melhorou.

## O problema com "parece melhor"

Na aula 2.1 você comparou um prompt fraco com um prompt forte lendo as duas saídas e
julgando qual era melhor. Isso funciona para ilustrar um conceito, mas não sobrevive ao uso
real, por três motivos:

- **Uma amostra não é evidência.** O modelo é estocástico: a mesma chamada pode gerar
  saídas diferentes. A saída boa que você viu pode ter sido sorte — e a ruim, azar.
- **Você olha o caso fácil.** Ao testar à mão, ninguém testa a mensagem ambígua, o campo
  vazio, o texto em outro idioma. Você testa o caso que tinha em mente ao escrever o prompt.
- **Melhorar aqui é piorar lá.** Você adiciona uma regra ao prompt para consertar um caso e
  quebra outro que já funcionava, sem perceber — porque não reexecutou o que já funcionava.

A aula 2.3 resolveu a **validade** da saída: com `json_schema`, o JSON sempre valida. Mas
validar não é acertar — um JSON perfeitamente formatado pode conter a categoria errada. Eval
é como você mede o acerto.

## A anatomia de um eval

```
1. Dataset fixo    → N casos, cada um com a entrada e o resultado esperado (gabarito)
2. Critério        → como decidir, automaticamente, se a saída conta como acerto
3. Execução        → roda os N casos contra o prompt e agrega (ex: taxa de acerto)
4. Comparação      → mesmo dataset, prompt A vs. prompt B — só o prompt muda
```

O item que as pessoas erram é o **1**: o dataset precisa ser *fixo*. Se você muda o prompt e
o dataset ao mesmo tempo, os dois números não são comparáveis e você não aprendeu nada.

## Os três tipos de critério — em ordem de preferência

| Critério | Como funciona | Quando usar |
|---|---|---|
| **Determinístico** | `==`, regex, validação de schema, parsing | Sempre que a tarefa tiver resposta certa: classificação, extração de campos, roteamento, formato |
| **LLM-as-judge** | Um segundo modelo avalia a saída contra uma rubrica | Tarefa aberta sem resposta única: resumo, tom, redação |
| **Humano** | Você lê e julga | Calibrar os dois acima; decisões de alto risco |

A regra prática: **não use um LLM como juiz quando um `==` resolve**. O critério
determinístico é mais barato, instantâneo, não tem variação entre execuções e não precisa
ser ele mesmo validado. Muita gente pula direto para LLM-as-judge por parecer mais
sofisticado, e passa a ter dois componentes não confiáveis em vez de um.

Quando LLM-as-judge for inevitável, duas precauções: dê ao juiz uma **rubrica explícita**
(critérios e escala, não "isso está bom?"), e prefira que ele **compare duas saídas** a
atribuir uma nota absoluta — modelos são bem mais consistentes em comparação do que em
notas.

## Como montar o dataset

Comece com **10 a 20 casos escritos à mão** — é o suficiente para detectar diferenças
grosseiras entre prompts, e você consegue fazer numa tarde. Não espere ter um dataset grande
para começar a medir.

O que precisa estar dentro:

- Casos **fáceis** (o comportamento óbvio, que você não quer quebrar depois).
- Casos de **borda**: entrada ambígua, dois assuntos na mesma mensagem, intenção implícita.
- Os casos que **já falharam** em produção ou em testes manuais — todo bug vira um caso do
  dataset, e é assim que o eval cresce naturalmente.

Um dataset só com casos óbvios dá 100% em qualquer prompt e não distingue nada.

## Dois cuidados na execução do eval

Duas escolhas de parâmetro decidem se o número que você vai obter mede o prompt ou mede
outra coisa:

- **`temperature=0`.** A diferença observada precisa vir do prompt, não da aleatoriedade da
  amostragem (aula 1.3). Com temperatura alta, rodar o mesmo eval duas vezes dá números
  diferentes e você não sabe a qual acreditar.
- **`max_tokens` com folga.** Se a saída for cortada no meio, o eval está medindo
  truncamento, não qualidade — e um prompt verboso vai parecer pior do que é.

E na hora de ler o resultado: **só os casos que falharam interessam**. A lista de acertos
não ensina nada; a lista de erros é a pauta da próxima iteração do prompt.

## Um critério estrito pode medir a coisa errada

Este é o erro mais instrutivo do tema, e vale examiná-lo antes de escrever seu próprio eval.

Considere uma tarefa de classificação de mensagens de suporte em quatro categorias fechadas
(`cobranca`, `tecnico`, `cancelamento`, `elogio`), comparando um prompt vago com um prompt
que lista as categorias. O critério de acerto é o mais óbvio possível: comparação exata
entre a saída e o gabarito. O prompt vago tira **0 de 10**. Mas olhe o que ele respondeu:

```
esperado='cobranca'      obtido='# Classificação: **Faturamento/Cobrança**...'
esperado='tecnico'       obtido='# Classificação: **Problema técnico / instabilidade...'
esperado='cancelamento'  obtido='# Classificação: **Cancelamento/encerramento de contrato**'
```

Ele **acertou a classificação** nesses casos. Tirou 0% porque respondeu em markdown, com
título e negrito — a comparação exata reprovou o formato, não o conteúdo. O eval estava
somando duas falhas distintas num único número:

| Falha | Causa | Como se corrige |
|---|---|---|
| **Formato** | Nada no prompt restringe a forma da saída | Restringir o formato, ou usar `json_schema` (aula 2.3) |
| **Categoria** | O modelo não sabe quais categorias existem, e inventa as próprias | Listar as categorias e dar regra de desempate |

Um "0% → 100%" assim é verdadeiro e inútil para diagnóstico: ele não diz o que consertar. A
correção é medir **duas métricas separadas**:

| Métrica | Pergunta que responde | Como se verifica |
|---|---|---|
| **Formato válido** | Meu código consegue usar essa resposta direto? | A saída é exatamente o nome de uma categoria, e nada mais |
| **Categoria correta** | O modelo entendeu a tarefa? | Extrair a categoria mencionada, tolerando saída verbosa, e comparar com o gabarito |

Com a separação, o retrato do prompt vago fica honesto e muito mais informativo: **formato
péssimo, categoria intermediária** — ele entende o problema, mas inventa rótulos que não
existem no conjunto (`acesso/login`, `reclamação`) e não obedece a forma pedida. São dois
consertos diferentes, e agora você sabe quais.

A lição generalizável: **seu critério de acerto tem que isolar a capacidade que você quer
medir.** Se ele mistura formato com conteúdo, o número cai mas não aponta para nenhuma ação.
Quando as duas coisas importam — e normalmente importam — meça as duas.

## Eval como teste de regressão

Um eval não é uma medição que você faz uma vez e arquiva — é uma **suíte que você reexecuta**.
A partir do momento em que existe, ele responde perguntas que antes eram achismo:

- Trocar `claude-haiku-4-5` por um modelo maior melhora o quanto, e vale o custo (aula 1.2)?
- Aquela frase que você adicionou ao system prompt para consertar um caso quebrou outros?
- A refatoração do prompt que "não deveria mudar nada" realmente não mudou nada?

O que transforma o eval em rede de proteção é fixar um **limiar mínimo de acerto**: abaixo
dele, a mudança não passa. É o mesmo papel de um teste vermelho — e no módulo 9 o eval volta
como parte do fluxo de CI, ao lado dos testes de código.

## Erros comuns

| Erro | Consequência |
|---|---|
| Mudar prompt e dataset na mesma iteração | Os números deixam de ser comparáveis; você não sabe o que causou a diferença |
| Dataset só com casos fáceis | 100% em qualquer prompt; o eval não distingue nada |
| LLM-as-judge onde `==` resolveria | Mais custo, mais lentidão e um avaliador que também erra |
| Juiz usando o mesmo modelo e prompt do avaliado | O juiz herda exatamente os mesmos vieses que deveria detectar |
| `temperature` alta durante o eval | Variação entre execuções mascara o efeito do prompt |
| Critério que mistura formato e conteúdo | O número cai, mas não indica o que corrigir (ver seção acima) |
| `max_tokens` apertado demais no eval | A saída é truncada e você mede truncamento, não qualidade |
| Rodar o eval só uma vez, antes de subir | Perde o valor principal, que é detectar regressão nas mudanças seguintes |

## Pontos-Chave

✅ "Parece melhor" não é medição: uma amostra não distingue prompt bom de sorte na amostragem.
✅ Um eval é dataset fixo + critério objetivo — se o dataset muda junto com o prompt, não há comparação.
✅ Prefira critério determinístico; use LLM-as-judge só para tarefas sem resposta única, com rubrica explícita.
✅ 10–20 casos à mão já servem; todo bug encontrado vira um caso novo no dataset.
✅ O critério tem que isolar o que você quer medir: formato e conteúdo são falhas diferentes, com correções diferentes.
✅ Use `temperature=0` no eval, para medir o prompt e não a aleatoriedade.
✅ O valor maior do eval é como teste de regressão a cada mudança de prompt ou de modelo.
