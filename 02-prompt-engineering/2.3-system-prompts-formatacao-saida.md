# 2.3 — System Prompts e Formatação de Saída

> **System prompt**: instrução separada da conversa que define o papel, tom e regras
> gerais do modelo — aplicada a toda a interação, não a uma mensagem específica.

## Por que usar um system prompt em vez de colocar tudo na mensagem do usuário

| | Na mensagem do usuário | No `system` |
|---|---|---|
| Escopo | Vale só para aquela mensagem | Vale para toda a conversa |
| Clareza para o modelo | Instrução se mistura com a pergunta do usuário | Separação clara entre "papel" e "pedido" |
| Reuso | Precisa repetir a cada chamada | Definido uma vez, reaproveitado em várias chamadas |
| Cache de prompt | Menos eficiente | Mais eficiente (o `system` é a parte mais estável do prompt) |

Use o `system` para definir: papel/persona, tom, restrições permanentes (idioma, limite de
tamanho, o que nunca fazer) e regras de formatação que devem valer sempre.

## Exemplo em Python — system prompt

Código completo: [`exemplos-python/2.3_system_prompt_e_saida_estruturada.py`](exemplos-python/2.3_system_prompt_e_saida_estruturada.py)

```python
response = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=200,
    system=(
        "Você é um assistente de suporte técnico para um provedor de internet residencial. "
        "Responda sempre em português, em no máximo 3 frases, e nunca prometa prazos "
        "que o cliente não informou."
    ),
    messages=[{"role": "user", "content": "Minha internet está lenta, o que eu faço?"}],
)
```

## Formatação de saída: da instrução em texto ao schema garantido

A forma mais simples de pedir um formato é descrevê-lo no prompt ("responda em JSON com os
campos X, Y, Z"). Isso funciona na maioria das vezes, mas não é **garantido** — o modelo
pode adicionar texto antes/depois do JSON, ou errar um campo.

Para garantir que a saída sempre seja um JSON válido conforme um schema, use
`output_config.format` com `json_schema`:

```python
response_json = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=200,
    messages=[{"role": "user", "content": "Extraia os dados: '...'"}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "nome": {"type": "string"},
                    "email": {"type": "string"},
                    "plano": {"type": "string"},
                },
                "required": ["nome", "email", "plano"],
                "additionalProperties": False,
            },
        }
    },
)
```

Com isso, a resposta é sempre um JSON que valida contra o schema — sem preâmbulo, sem
markdown, sem risco de campo faltando. Compare com pedir "responda em JSON" apenas por
instrução: essa segunda forma pode falhar ocasionalmente e por isso não deve ser usada
quando seu código depende de fazer `json.loads()` na resposta sem tratamento de erro.

## Quando usar cada abordagem

| Situação | Abordagem |
|---|---|
| Protótipo rápido, formato simples, você vai revisar manualmente | Pedir o formato via instrução no prompt |
| Sua aplicação faz parsing automático da resposta (ex: `json.loads`) | `output_config.format` com `json_schema` |
| Você precisa validar tipos de campo (string, número, booleano) | `output_config.format` com `json_schema` |
| Regras que valem para toda a conversa | `system` |

## Pontos-Chave

✅ `system` separa "papel/regras" de "pedido do usuário" e é reaproveitado em toda a conversa.
✅ Pedir um formato só por instrução no prompt não garante validade — o modelo pode desviar.
✅ `output_config.format` com `json_schema` garante que a saída sempre valide contra o schema.
✅ Use saída estruturada sempre que seu código for processar a resposta automaticamente.
