# 6.1 — O que é Spec-Driven Development

> **Spec-Driven Development (SDD)**: metodologia onde você escreve uma especificação
> clara e estruturada do que precisa ser construído **antes** de pedir para uma IA (ou
> humano) implementar — em vez de descrever o problema vagamente e iterar até acertar.

## O problema do "vibe coding"

"Vibe coding" é o apelido informal para pedir código a partir de um prompt vago e ir
ajustando por tentativa e erro, sem definir de antemão regras de negócio, casos de borda
ou formato de saída. Funciona para protótipos descartáveis, mas em código que vai para
produção, o custo aparece depois: bugs em casos de borda que ninguém especificou,
retrabalho porque a IA "interpretou" o pedido de um jeito diferente do esperado.

```
"Crie uma função para validar CPF."
```

Esse prompt não define: o que fazer com entrada malformada? CPFs com todos os dígitos
iguais são inválidos mesmo passando no cálculo? A função deve aceitar CPF formatado
("529.982.247-25") ou só números? Cada uma dessas lacunas é uma decisão que a IA vai tomar
por conta própria — e pode não ser a decisão certa para o seu caso.

## O que muda com uma especificação

Uma spec força você (ou quem escreve o pedido) a tomar essas decisões **antes**, de forma
explícita — o que reduz drasticamente o espaço de interpretação da IA:

```
Função: validar_cpf(cpf: str) -> bool

Regras:
1. Remover caracteres não numéricos antes de validar.
2. CPF deve ter exatamente 11 dígitos após a limpeza.
3. Rejeitar CPFs com todos os dígitos iguais.
4. Validar os dois dígitos verificadores segundo o algoritmo oficial.

Saída: True/False. Não deve lançar exceção para entrada malformada.

Casos de teste esperados:
- validar_cpf("529.982.247-25") -> True
- validar_cpf("11111111111") -> False
```

## Por que SDD funciona melhor com IA do que sem estrutura

Um LLM (módulo 1) prevê a continuação mais **plausível**, não necessariamente a que você
tinha em mente. Sem uma especificação, ele preenche as lacunas do jeito mais comum/genérico
— que pode não ser certo para o seu contexto específico. Uma spec elimina a ambiguidade
antes que ela vire código errado, e serve como **contrato verificável**: dá para checar se
a implementação bate com o que foi especificado.

## SDD não é burocracia desnecessária

Isso não significa escrever specs formais de 10 páginas para toda mudança pequena. SDD é
uma escala: para um ajuste trivial, uma frase clara já é "spec" suficiente. Para uma
funcionalidade nova com regras de negócio não óbvias, vale investir numa especificação
mais estruturada — o retorno é proporcional à complexidade e ao risco de interpretação
errada.

## Pontos-Chave

✅ SDD define o que construir (regras, entrada/saída, casos de borda) antes de pedir a implementação.
✅ Vibe coding funciona para protótipos, mas acumula retrabalho em código de produção.
✅ Uma spec reduz o espaço de interpretação do LLM — menos decisões implícitas tomadas por ele.
✅ O nível de detalhe da spec deve ser proporcional à complexidade e ao risco da tarefa.
