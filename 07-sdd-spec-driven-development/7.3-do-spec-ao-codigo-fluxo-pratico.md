# 7.3 — Do Spec ao Código: Fluxo Prático

> O fluxo spec-driven completo tem quatro etapas: **spec → plano → implementação →
> verificação**. Cada etapa é uma checagem antes de avançar para a próxima, em vez de ir
> direto da ideia para o código.

## As quatro etapas

```
1. SPEC          — define o que construir (aula 7.2)
        │
        ▼
2. PLANO         — como implementar, antes de escrever código de fato
        │
        ▼
3. IMPLEMENTAÇÃO — o código, gerado a partir da spec + plano
        │
        ▼
4. VERIFICAÇÃO   — checar se a implementação atende a spec (casos de teste)
```

Pular direto da spec para a implementação funciona para tarefas simples. Para tarefas mais
complexas, o **plano** intermediário vale a pena: é mais barato revisar (e corrigir) um
plano em bullet points do que revisar código já escrito — e a **verificação** final
confirma que nada foi esquecido no caminho.

## Exemplo em Python — as quatro etapas em sequência

Código completo: [`exemplos-python/7.3_fluxo_spec_plano_implementacao.py`](exemplos-python/7.3_fluxo_spec_plano_implementacao.py)

```python
# 1. PLANO
plano = perguntar(f"Com base na especificação, descreva o plano de implementação "
                   f"em bullet points. Não escreva código ainda.\n\n{spec}")

# 2. IMPLEMENTAÇÃO
codigo = perguntar(f"Implemente a função seguindo esta spec e plano...\n\n{spec}\n\n{plano}")

# 3. VERIFICAÇÃO
verificacao = perguntar(f"Verifique se o código atende TODOS os casos de teste da "
                         f"especificação...\n\n{spec}\n\n{codigo}")
```

Cada etapa usa o resultado da anterior como entrada — isso é o mesmo princípio de
"decompor em subtarefas" que vimos em multi-agente (aula 4.3), aplicado especificamente ao
ciclo de desenvolvimento de software.

## Por que a etapa de verificação importa

A verificação em texto (pedir ao modelo para "checar mentalmente" os casos de teste) é
útil, mas **não substitui rodar os testes de verdade**. Trate essa etapa como uma primeira
triagem barata — ela pega erros óbvios rapidamente — mas sempre execute os testes reais
antes de considerar a tarefa concluída (isso conecta com o módulo 9, sobre IA em testes e
revisão).

## Esse fluxo é o que harnesses de agentic coding automatizam

O harness do módulo 6 automatiza exatamente esse ciclo — muitas vezes com um passo de
planejamento explícito antes de tocar em código, e rodando testes de verdade como parte da
verificação. Ou seja: o SDD desta aula não é uma alternativa ao harness, é **a metodologia
que você aplica dentro dele**. O ciclo manual que percorremos aqui é o mesmo que o Claude
Code executa por baixo — e é por isso que vale conhecê-lo: quando o resultado automático não
sai como esperado, você sabe em qual etapa intervir.

## Quando simplificar o fluxo

Para mudanças pequenas e de baixo risco, um plano formal separado pode ser exagero — spec
clara + implementação + rodar os testes já é suficiente. Reserve o plano intermediário
explícito para mudanças que tocam várias partes do sistema, ou onde o "como" não é óbvio a
partir do "o quê".

## Pontos-Chave

✅ O fluxo completo é spec → plano → implementação → verificação, cada etapa uma checagem antes de avançar.
✅ Um plano intermediário é mais barato de revisar/corrigir do que código já escrito.
✅ Verificação em texto é uma triagem útil, mas não substitui rodar testes de verdade.
✅ Harnesses de agentic coding automatizam esse fluxo — entendê-lo manualmente ajuda a saber quando intervir.
