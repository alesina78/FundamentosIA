# 7.2 — Escrevendo Specs Eficazes para IA

> Uma especificação eficaz não precisa ser extensa — precisa ser **inequívoca** nos pontos
> que importam: entrada, saída, regras de negócio e casos de borda.

## Anatomia de uma spec eficaz

| Seção | Pergunta que responde |
|---|---|
| **Objetivo** | Por que essa funcionalidade existe? Qual problema resolve? |
| **Entrada/Saída** | Que dados entram, em que formato? O que sai, em que formato? |
| **Regras de negócio** | Quais validações, cálculos ou restrições se aplicam? |
| **Casos de borda** | O que acontece com entrada vazia, inválida, extrema, duplicada? |
| **Casos de teste** | Exemplos concretos de entrada → saída esperada |
| **Fora de escopo** (opcional) | O que explicitamente NÃO deve ser feito nessa etapa |

A seção de **casos de teste** é a que mais reduz ambiguidade: exemplos concretos deixam
claro o comportamento esperado de um jeito que descrição em prosa às vezes não consegue.

## Erros comuns ao escrever specs

| Erro | Consequência |
|---|---|
| Definir "o que" mas não "o que fazer quando algo dá errado" | IA inventa o comportamento de erro |
| Omitir o formato exato de entrada/saída | Implementação pode usar um formato diferente do esperado |
| Specs longas demais, misturando várias funcionalidades | Difícil verificar se a implementação atende tudo |
| Assumir que "óbvio para mim" é óbvio para a IA | Regras de negócio do seu domínio raramente são óbvias sem estarem escritas |

## Usando a própria IA para revisar sua spec

Antes de pedir a implementação, vale usar o LLM para **revisar a spec** e apontar
ambiguidades ou casos de borda esquecidos — uma etapa barata que evita retrabalho maior na
implementação.

Código completo: [`exemplos-python/7.2_revisar_spec_com_ia.py`](exemplos-python/7.2_revisar_spec_com_ia.py)

```python
def revisar_spec(spec: str) -> str:
    prompt = f"""\
Você é um revisor técnico. Analise a especificação abaixo e liste:
1. Ambiguidades — pontos que podem ser interpretados de mais de uma forma.
2. Casos de borda não cobertos.
3. Perguntas que você faria ao autor antes de implementar.

Não implemente nada — apenas revise a especificação.

Especificação:
{spec}
"""
    ...
```

Rode o exemplo com a spec de `aplicar_desconto` — repare que o modelo provavelmente
apontará perguntas como: "o que acontece se `percentual_desconto` for negativo ou maior
que 100? o preço final pode ser negativo?" — exatamente o tipo de lacuna que, se não
resolvida antes, vira um bug depois.

## Template mínimo reutilizável

```
Função/Funcionalidade: <nome>

Objetivo: <por que existe>

Entrada: <tipo e formato>
Saída: <tipo e formato>

Regras:
1. ...
2. ...

Casos de borda:
- Entrada vazia/nula: ...
- Valores extremos: ...
- Entrada inválida: ...

Casos de teste:
- <entrada> -> <saída esperada>
```

## Pontos-Chave

✅ Uma spec eficaz é inequívoca em entrada, saída, regras e casos de borda — não precisa ser longa.
✅ Casos de teste concretos reduzem ambiguidade melhor do que descrição em prosa.
✅ Usar a própria IA para revisar a spec antes de implementar é uma etapa barata que evita retrabalho.
✅ Regras de negócio do seu domínio raramente são "óbvias" para a IA — escreva-as explicitamente.
