# 6.2 — Criando e testando um Hook

> **Hook**: um ponto de extensão do harness que executa código **seu** (não do modelo) em
> momentos específicos do ciclo do agente. Nesta aula você vai criar um hook de verdade:
> um registro automático de memória do que a IA fez, gravado dentro de um vault do Obsidian.

## O que é um hook, e por que ele existe

O loop agentic da aula 4.2 é probabilístico: o modelo *decide* o que fazer. Isso é ótimo para
flexibilidade e péssimo para garantias. Se você quer que algo aconteça **sempre** — um log,
uma validação, uma formatação — pedir no prompt não basta: em algum momento o modelo vai
esquecer, reinterpretar ou ser convencido do contrário.

Um hook resolve isso movendo a regra para fora do modelo. Ele roda **deterministicamente**,
disparado pelo harness, no evento que você escolher:

| Evento | Quando dispara | Uso típico |
|---|---|---|
| `PreToolUse` | Antes de uma ferramenta executar | Bloquear ações perigosas, validar entrada |
| `PostToolUse` | Depois que a ferramenta termina | Formatar código, rodar linter, auditar |
| `UserPromptSubmit` | Quando você envia uma mensagem | Injetar contexto extra |
| `SessionStart` | Ao abrir a sessão | Carregar estado do projeto |
| `Stop` | Quando o agente termina o turno | Notificar, registrar resumo |

A regra mental: **hook é para garantia, prompt é para intenção.** Se falhar for inaceitável,
é hook. Se for uma preferência, pode ser prompt/CLAUDE.md.

## O caso desta aula: memória da IA no Obsidian

O problema: cada sessão com o agente produz decisões e aprendizados que se perdem quando o
contexto é descartado. Você quer um registro externo, durável e pesquisável — e o Obsidian
(um vault de arquivos Markdown com links `[[wiki]]`) é exatamente isso.

A solução: um hook no evento `Stop` que, ao final de cada turno do agente, grava uma nota
diária no vault com o que foi feito. Repare no encaixe conceitual: isso é a **memória de longo
prazo** do agente (aula 4.3) implementada por fora do modelo, e o vault vira depois uma base
consultável — potencialmente por RAG (módulo 3).

## Anatomia de um hook no Claude Code

Um hook tem três partes:

1. **O evento** — onde no ciclo ele engancha.
2. **O matcher** — um filtro opcional (ex: só para a ferramenta `Write`).
3. **O comando** — um executável que recebe um JSON pelo `stdin` e responde pelo código de
   saída e/ou por um JSON no `stdout`.

A configuração vive no `settings.json` (em `~/.claude/settings.json` para valer em tudo, ou
em `.claude/settings.json` do projeto para valer só ali):

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python ~/.claude/hooks/memoria_obsidian.py"
          }
        ]
      }
    ]
  }
}
```

O contrato de comunicação é o ponto mais importante a entender:

| Direção | Mecanismo | Conteúdo |
|---|---|---|
| Harness → hook | `stdin` (JSON) | Evento, sessão, caminho do transcript, entrada da ferramenta |
| Hook → harness | Código de saída | `0` = segue; `2` = bloqueia a ação e devolve o `stderr` ao modelo |
| Hook → harness | `stdout` (JSON) | Decisão estruturada e contexto adicional a injetar |

O código de saída `2` é o que transforma um hook de observador em **guarda**: ele cancela a
ação e explica ao modelo o porquê.

[`exemplos-python/6.2_hook_memoria_obsidian.py`](exemplos-python/6.2_hook_memoria_obsidian.py)

## Testando o hook — o passo que quase todo mundo pula

Hook mal testado é pior que nenhum hook: ele falha em silêncio, e você só descobre quando
precisava dele. Teste em três camadas, sempre nesta ordem:

**1. Isolado, sem o harness.** O hook é só um programa que lê JSON do `stdin`. Rode-o na mão
com um payload de exemplo e confira o arquivo gerado. Se não funciona aqui, não vai funcionar
lá dentro.

**2. Dentro do harness, com o inspetor.** O comando `/hooks` lista os hooks registrados e a
flag `claude --debug` mostra cada disparo, com stdin, stdout e código de saída. É onde você
descobre os dois erros clássicos: o hook não está registrado (JSON inválido, evento com nome
errado) ou o `~` não expandiu no caminho.

**3. No caminho de falha.** Force o cenário ruim — vault inexistente, sem permissão de
escrita. Um hook que estoura exceção pode travar seu fluxo de trabalho inteiro; ele deve
falhar de forma silenciosa e não-bloqueante quando o problema é dele, não seu.

> ⚠️ **Segurança**: hooks rodam com as **suas** permissões de usuário, sem confirmação, a cada
> disparo. Nunca instale um hook de terceiros sem ler o código — o assunto volta na aula 6.5.

## Pontos-Chave

✅ Hook é código determinístico disparado pelo harness — é para **garantia**, não para intenção.
✅ Ele se configura em `settings.json`, por evento e matcher, e se comunica por stdin/stdout/exit code.
✅ Código de saída `2` bloqueia a ação e devolve a justificativa ao modelo.
✅ Um hook `Stop` gravando notas num vault Obsidian dá ao agente memória durável e pesquisável.
✅ Teste em três camadas: isolado, dentro do harness com `--debug`, e no caminho de falha.
