# 6.4 — Criando um Subagente

> **Subagent**: uma instância separada do agente, com contexto, instruções, modelo e
> permissões próprios, que o agente principal invoca para uma sub-tarefa. Nesta aula você vai
> criar um subagente especializado em escrever código Python.

## Por que delegar

O subagente resolve um problema concreto: **contaminação de contexto**. Uma sub-tarefa como
"vasculhe o repositório e descubra onde a autenticação é validada" pode consumir dezenas de
arquivos para produzir uma resposta de três linhas. Se isso roda no contexto principal, você
paga com a janela inteira poluída de material que já cumpriu seu papel.

Delegando, o subagente queima o próprio contexto na busca e devolve só a conclusão. É o
multi-agente da aula 4.3 — mas nativo do harness, sem você orquestrar nada.

Três motivos legítimos para criar um subagente:

- **Isolar contexto**: a sub-tarefa gera muito material intermediário e pouco resultado.
- **Especializar**: um prompt de sistema focado supera um agente generalista naquela tarefa.
- **Restringir**: dar a essa sub-tarefa um conjunto menor de ferramentas (ex: um revisor que
  só lê, nunca escreve) — segurança por construção, não por confiança.

E o principal motivo para **não** criar: cada subagente começa **frio**, sem nada do que já
foi conversado. Se a tarefa depende do contexto acumulado da sessão, delegar custa mais do que
economiza — o subagente vai redescobrir do zero o que você já sabia.

### Exemplos de quando criar

Cada exemplo abaixo se justifica por um dos três motivos — e é isso que você deve conseguir
apontar antes de criar qualquer subagente seu.

**Explorador de código** *(isolar contexto)*. "Onde neste repositório a sessão do usuário é
invalidada?" Ele abre dezenas de arquivos, segue imports, descarta caminhos falsos — e devolve
três linhas com os arquivos certos. Todo o material intermediário morre com ele. É o caso mais
clássico: **muita leitura, pouca conclusão**.

**Revisor de código** *(restringir)*. Um subagente com `tools: Read, Grep, Glob` — sem `Write`,
sem `Edit`. Ele aponta problemas mas é **incapaz** de "corrigir enquanto revisa", que é
justamente o vício que estraga uma revisão. A restrição aqui não é burocracia: é o que garante
que revisar e alterar continuem sendo dois passos separados.

**Escritor de testes** *(especializar)*. Um prompt de sistema dedicado a testes — cobrir os
casos de borda, nunca testar detalhe de implementação, nomear os testes pelo comportamento
esperado — produz resultado melhor que o mesmo pedido feito a um generalista, porque essas
regras ocupam o centro das instruções em vez de competir com outras cem.

**Investigador de bug** *(isolar contexto)*. Reproduzir a falha exige rodar o teste várias
vezes, ler stack traces longos e imprimir estado. Nada disso precisa sobreviver: o que interessa
no contexto principal é a causa raiz e o arquivo onde ela mora.

**Redator de documentação** *(especializar)*. Tom, formato e estrutura da documentação são
regras diferentes das de escrever código — e conflitam com elas se convivem no mesmo prompt.
Este próprio curso usa um subagente assim.

**Auditor de dependências ou de segurança** *(restringir + isolar)*. Varre `requirements.txt`,
changelogs e CVEs — muito material bruto — e só pode ler. Devolve uma lista curta de riscos.

### Exemplos de quando NÃO criar

O espelho é igualmente importante. Não delegue quando:

- **A tarefa depende do que já foi conversado.** "Agora aplique aquela mudança que discutimos"
  é impossível para quem chega frio.
- **A tarefa é curta.** Ler um arquivo e trocar uma linha não justifica montar um agente: o
  custo de partida é maior que o trabalho.
- **Você quer uma garantia, não uma delegação.** "Sempre rode o linter depois de editar" é
  hook (aula 6.2) — um subagente pode simplesmente não ser chamado.
- **É um procedimento que você mesmo pede.** Se a questão é "quais passos seguir", isso é
  skill (aula 6.3); subagente é para quando o trabalho precisa de contexto *próprio*.
- **O resultado precisa de ida e volta com você.** O subagente devolve um relatório final, não
  uma conversa — tarefas exploratórias em que você quer opinar no meio do caminho ficam no
  agente principal.

## Anatomia de um subagente

Um subagente é um arquivo Markdown com frontmatter, em `~/.claude/agents/` (global) ou
`.claude/agents/` (projeto):

```yaml
---
name: escritor-python
description: Escreve funções e módulos Python novos a partir de uma especificação.
             Use quando o pedido for criar código Python do zero.
tools: Read, Write, Edit, Glob, Grep, Bash
model: sonnet
---

Você escreve código Python de produção. Siga estas regras:

- Antes de escrever, leia arquivos vizinhos e siga as convenções existentes.
- Use type hints em toda assinatura pública e docstrings no estilo já adotado no projeto.
- Sem dependências novas sem necessidade — prefira a biblioteca padrão.
- Trate os casos de erro explicitamente; nada de `except: pass`.
- Ao terminar, rode o código ou os testes e relate o resultado real, sem suavizar falhas.
```

Os quatro campos que definem o comportamento:

| Campo | Papel |
|---|---|
| `name` | Identificador usado para invocar |
| `description` | **Quando** delegar — é o que o agente principal lê para decidir |
| `tools` | Ferramentas permitidas; omitir herda todas |
| `model` | Modelo a usar — permite tarefa simples em modelo mais barato |

Repare que `description` cumpre aqui o mesmo papel que na skill (aula 6.3): é o gatilho. E
`tools` é onde mora o ganho de segurança — um subagente de revisão sem `Write` **não pode**
alterar o código, independentemente do que o modelo decida.

## O corpo do arquivo é um prompt de sistema

Tudo abaixo do frontmatter substitui as instruções gerais para aquela instância. É onde a
especialização acontece de verdade — e o erro mais comum é escrever ali um texto genérico
("você é um programador experiente"), que não muda nada. Um bom prompt de subagente é
específico e verificável: convenções, o que evitar, e o que fazer antes de declarar pronto.

## Testando o subagente

Como na skill, separe as duas perguntas:

**1. Ele é acionado?** Peça algo em linguagem natural que deveria delegar ("escreva um módulo
Python que faça X") e veja se o subagente entra. Se não, ajuste a `description`. Também vale o
teste negativo: um pedido de *editar* código existente não deveria acionar um subagente cuja
descrição diz "criar do zero".

**2. O resultado respeita as regras?** Rode uma tarefa real e confira contra o prompt de
sistema, item por item: tem type hints? seguiu as convenções do projeto? tratou os erros?
Cada regra ignorada é uma regra vaga demais ou enterrada no meio do texto.

**3. As restrições de ferramenta valem?** Peça deliberadamente algo fora do `tools` declarado
e confirme que ele não consegue. Restrição não verificada é restrição imaginária.

Para isolar a segunda pergunta da primeira, invoque o subagente pelo nome.

## Hook, skill ou subagente?

| Mecanismo | O que resolve | Quem controla |
|---|---|---|
| **Hook** | Garantir que uma regra sempre se aplique | Seu código (determinístico) |
| **Skill** | Carregar conhecimento especializado só quando necessário | O agente decide quando carregar |
| **Subagente** | Isolar/paralelizar sub-tarefas com contexto e permissões próprios | O agente principal decide quando delegar |

Os três são complementares, não alternativas: um projeto maduro usa hooks para as garantias,
skills para os procedimentos e subagentes para o trabalho pesado isolado.

## Pontos-Chave

✅ Subagente = instância separada com contexto, prompt, modelo e ferramentas próprios.
✅ Delegue para isolar contexto, especializar ou restringir ferramentas — não por hábito.
✅ Ele começa frio: tarefa que depende do contexto da sessão não deve ser delegada.
✅ Define-se num `.md` com frontmatter em `.claude/agents/`; a `description` é o gatilho e `tools` é a trava de segurança.
✅ Teste em três frentes: se é acionado, se segue o prompt de sistema, e se a restrição de ferramentas realmente vale.
